Security model

What Diffhold guarantees, what it trusts, and what is still open. The full threat model, with 25 threats and the evidence for each, is docs/threat-model.md in the repository.

Guarantees

  • No agent write without a matching grant. Every request from an agent ServiceAccount is checked by the admission webhook against a grant Diffhold issued for that call.
  • A grant covers one change. It names the verb and objects, and either the approved replica count or a SHA-256 hash of the exact object the dry-run predicted. It is used once and expires (30 seconds by default).
  • An approval covers one diff. It is bound to the change the approver saw, used once and expires.
  • People and controllers are never blocked. The webhook's matchConditions limit it to agent namespaces, so a Diffhold outage only stops agent writes.
  • Agent RBAC is still the ceiling. Diffhold can only narrow what the agent's ServiceAccount is already allowed to do.

What it trusts

BoundaryControl
Gateway → DiffholdMutual TLS with a pinned client name. The agent identity comes from gateway metadata, never from request headers.
Grants in agent namespacesHMAC-SHA256 over the grant, the Secret's name and UID, with a key in Diffhold's namespace that agents can't read. A tampered grant is denied and revoked.
Used-grant markersCreated atomically in Diffhold's namespace, out of the agent's reach.
PoliciesRead only from Diffhold's namespace by default. A policy's ServiceAccount must be in an agent namespace and used by one policy only.
ApproversTheir own token, checked by TokenReview with a dedicated audience. The agent and agent-namespace ServiceAccounts can't approve.
EvidenceHash-chained audit log. Secret values and policy-chosen paths are redacted; approvals stay bound to the unredacted change.

Known limitation

kubernetes-mcp-server applies changes client-side, while Diffhold predicts them with a server-side apply. When an apply removes fields, the two can differ, and the backstop then denies the write. This fails closed.

Reporting a vulnerability

Until the source repository is public, report security issues privately through GitHub private vulnerability reporting on this site's repository. Do not open a public issue.
